<summary><b>⬡ &nbsp;Orion — Enterprise RAG Platform</b></summary>

<br/>

Orion is a production-grade Retrieval-Augmented Generation platform built for enterprise knowledge operations. It powers intelligent document Q&A, policy compliance checking, and internal knowledge retrieval for Fortune 500 clients — processing millions of tokens daily with sub-300ms median latency. The system combines a hybrid retrieval layer (dense + sparse), dynamic context window management, and a hallucination-detection layer trained on domain-specific corpora.

| Attribute | Detail |
|---|---|

| **Scale** | 4M+ documents indexed · 2M+ queries/month · 99.95% uptime SLA |
| **Performance** | p50 latency 280ms · p99 latency 890ms · throughput 1,200 req/s |
| **Security** | SOC 2 Type II compliant · tenant data isolation · field-level encryption at rest |
| **Impact** | Reduced analyst research time by 68% · $2.4M ARR attributed to platform |
| **Repository** | [![GitHub](https://img.shields.io/badge/GitHub-orion--rag-6366f1?style=flat-square&logo=github)](https://github.com/AlexVoss/orion-rag) |

The citation-grounded generation pipeline enforces source attribution at the sentence level, reducing hallucination rates to under 2% on the evaluation suite.

<summary><b>⬡ &nbsp;Nexus — Distributed API Gateway</b></summary>

<br/>

It handles authentication, rate limiting, request routing, circuit breaking, and telemetry aggregation as a unified control plane — removing cross-cutting infrastructure concerns from individual service teams and consolidating observability into a single pane.

| Attribute | Detail |
|---|---|
| **Stack** | Go, Rust (core proxy), Redis Cluster, Prometheus, Grafana, Kubernetes, Helm |
| **Scale** | 200M+ requests/day · 600+ microservices in mesh · deployed across 4 AWS regions |
| **Performance** | p50 gateway overhead 1.2ms · p99 2.8ms · 99.999% availability |
| **Security** | mTLS between all services · RBAC policy engine · JWT validation at edge |
| **Impact** | Consolidated 11 disparate auth implementations · reduced incident MTTR by 52% |
| **Repository** | [![GitHub](https://img.shields.io/badge/GitHub-nexus--gateway-6366f1?style=flat-square&logo=github)](https://github.com/AlexVoss/nexus-gateway) |

The Nexus proxy core is written in Rust using Tokio's async runtime, achieving single-digit millisecond p99 latency even at peak traffic. A declarative YAML policy engine allows platform teams to define routing rules, retry budgets, and security policies without code changes, reducing time-to-configure for new services from days to under an hour.

<details>
<summary><b>⬡ &nbsp;Stratum — ML Feature Store</b></summary>

<br/>

Stratum is a unified feature store and data serving layer for machine learning teams operating across training, evaluation, and online inference contexts. It eliminates the training-serving skew problem by guaranteeing consistent feature computation across offline batch pipelines and online low-latency serving paths — a critical correctness property for production ML systems.

| Attribute | Detail |
|---|---|
| **Stack** | Python, Apache Spark, Apache Kafka, Redis, PostgreSQL, FastAPI, Airflow, GCP |
| **Scale** | 800+ registered features · 50+ models in production · 5TB+ feature data materialized daily |
| **Performance** | Online serving p50 8ms · batch backfill 1.2TB/hr · point-in-time correct joins |
| **Security** | Feature lineage tracking · GDPR deletion propagation · audit logs on all reads |
| **Impact** | Reduced feature engineering duplication by 70% across 12 ML teams |
| **Repository** | [![GitHub](https://img.shields.io/badge/GitHub-stratum--featurestore-6366f1?style=flat-square&logo=github)](https://github.com/AlexVoss/stratum-featurestore) |

Stratum implements a **time-travel query interface** allowing models to retrieve feature values as they existed at any historical timestamp — enabling correct offline training data generation without label leakage. The platform integrates natively with MLflow experiment tracking, automatically logging feature snapshots alongside model artifacts for full reproducibility.

<br/>

</details>

<details>
<summary><b>⬡ &nbsp;Pulsar — Real-Time Analytics Engine</b></summary>

<br/>

Pulsar is a real-time event analytics engine built to power product intelligence dashboards, anomaly detection systems, and customer behavior analytics for SaaS platforms. It ingests structured event streams, applies configurable aggregation pipelines, and surfaces metrics to end consumers within a 3-second end-to-end latency target — all at scale, without the operational overhead of a traditional data warehouse.

| Attribute | Detail |
|---|---|
| **Stack** | Apache Kafka, Apache Flink, ClickHouse, Python, TypeScript, React, AWS Kinesis |
| **Scale** | 900M+ events/day · 150+ active dashboards · sub-3s end-to-end latency |
| **Performance** | ClickHouse queries p99 under 200ms · Flink job 99.8% state recovery on restart |
| **Security** | Row-level tenant isolation in ClickHouse · encrypted event payloads in transit |
| **Impact** | Replaced 6-hour batch reporting cycle with real-time intelligence for 3 product lines |
| **Repository** | [![GitHub](https://img.shields.io/badge/GitHub-pulsar--analytics-6366f1?style=flat-square&logo=github)](https://github.com/AlexVoss/pulsar-analytics) |

Pulsar's Flink topology applies a two-phase windowing strategy: a tumbling micro-batch window for low-latency approximate counts, followed by a session-based exact aggregation pass for financial reporting accuracy. ClickHouse's columnar storage engine powers the dashboard query layer, returning complex analytical queries over 90-day windows in under 200ms at p99.
